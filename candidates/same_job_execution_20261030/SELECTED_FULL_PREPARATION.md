# Selected-profile original FULL preparation

This is an opt-in host preparation contract, not a new hardware profile, numerical
method, runtime build, or execution approval. All five original M128 profiles
remain registered on the same 4096-MAC / 32-lane Chisel artifact. Exact original
full-block output, all experts, official TorchTopK, cache state, source identity,
process ownership and resource checks remain required. No five-profile PASS can
be inferred from a proper subset.

## Authority and scope

The externally approved cloud lifecycle budget may include `execution_policy`
constructed by `profile_policy.selected_policy([1, 2, 3, 4])`, or another exact,
nonempty, sorted integer subset of 0 through 4. The binding, approved budget and
ordinary FULL V3 ready queue must specify the same selection. The approval must
pin the new budget hash. A standalone shortened inventory, a CLI selection, CPU
observation, old approval or changed JSON `approved` flag does not grant authority.
Calibration, stage coverage and first-fault modes cannot use this policy.

The old no-policy/full-five and DEFER paths retain their original contracts.
P0 still requires the original AVX512 host capability whenever it is selected.
A non-P0 selection does not qualify P0 or emulate its CPU contract. The host
observation must describe the actual CPU, including a false AVX512 observation.

## Original dependency projection

- Runtime archives are the exact filename/hash/size union derived from the
  immutable original lock metadata, for only the selected runtime families.
  Full-five remains 53 archives. P1–P4 together require 40 archives,
  287,899,273 bytes. Same-runtime profiles do not gain each other's leases.
- Fresh installs and existing-byte revalidation emit separately versioned
  selected owner and receipt schemas. They preserve the original installer,
  wrapper, tree manifest, source sidecar, import validation and strict cleanup.
- Weight selection is reconstructed from the original70 plan and complete
  profile geometry, not a caller's filtered rows. Every selected block is whole,
  including every MoE expert. Original range limits, hash/source-membership
  checks, safetensors headers and official configuration remain authoritative.
- Software reference generation uses the unchanged original producer and job.
  The new wrapper additionally verifies complete tensor/state geometry, seed,
  runtime/sidecar identity and strict phase/native ownership. It cannot label
  software references as DUT evidence.

## Existing material reuse

Selected reuse is explicit `RETAINED_SELECTED_M128_MATERIALS_V1`, not a shortened
legacy70 manifest. It pins the completed original controller, source catalog,
weight acquisition summary and native receipt, reference index and selected
reference receipts. A selected original producer also pins its acquisition
binding and derived selection plan. Only selected payloads and runtimes are read;
shared original metadata remains pinned to establish their source provenance.
A fresh-install source additionally pins the original owner manifest.

When reusing data with a model-candidate artifact, the independent model review
must contain `MODEL_CANDIDATE_SELECTED_DATA_REFERENCE_ONLY_V1`, with the exact
selected weight/reference domains, original producer source closure, all five
registered profiles, original M128/routing contract and any already-required
finite-watchdog relation. It grants data reuse only, never historical owner
liveness, runtime PASS, DUT PASS or final RTL qualification.

## Integration and evidence

Keep every modified/new source and test in the executor source catalog. Reusing
an existing build additionally requires an externally reviewed exact host-only
adaptation for the new catalog; the narrowly enumerated source paths do not waive
that review. The original Chisel, generated artifact, driver, installer source,
reference producer, stimulus and five-profile acceptance predicate are unchanged.

Run the selected preparation, selected runtime, selected material and existing
cloud/FULL tests before an approved launch. These tests use synthetic authority
and mocked execution boundaries. They prove admission and dependency selection,
not a completed full numerical prefill or final RTL replay. No new automatic
launch, download, retry, submission or publication is introduced.
